# Repository tooling

Release, packaging and check scripts run end to end only when their moment comes (a release, a tag, a CI job), so a wrong assumption in them stays hidden until it blocks that moment. Write each one so it cannot depend on the machine, the timing or the package mix it was first written against.

- **Read only paths a tool promises as output, or paths you create.** The same script runs on CI and on maintainer machines whose tools are configured differently (Cargo `build.build-dir` moves `cargo package`'s unpacked copy and other intermediates out of `target/`; a `RUSTC_WRAPPER` can fail on its own). `target/package/*.crate` is Cargo's promised output; its unpacked verification copy is not. To test packaged bytes, extract the archive yourself into a fresh `mkdtemp` directory outside the repository: Cargo treats a manifest under the `rust/` workspace root as an undeclared member and refuses it.
- **A readback right after a remote write decides nothing.** Registries and APIs expose a write seconds to minutes after it returns. Poll until it appears, bounded by a deadline (`awaitPublished` in `registry-integrity.ts`); only an explicit not-found keeps waiting, and outages or malformed answers still stop at once. Never sleep a fixed time and then read once.
- **Rules about the npm package and the Rust crate hold per package.** They have separate registry histories, first publications and release selections: the crate started at 0.6.0 while npm started earlier. A version existing in Git or on one registry proves nothing about the other. Test each such rule with the packages diverging, not only with both present.
- **Before working around a script's step by hand, read how the script handles it.** Release preparation already deletes stale evidence when a tag moves; manual cleanup there only risks deleting retained evidence the recovery procedure needs.
